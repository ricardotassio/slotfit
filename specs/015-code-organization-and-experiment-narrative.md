## Purpose

Make the repository readable as a study: organize the Python package along
SOLID, Clean Code, GRASP and Object Calisthenics without changing behaviour, and
rewrite the README as a sequential account of the experiment (problem,
hypothesis, stages, decisions, evidence, no-go) with screenshots generated from
the running application.

## Scope

### Code organization (behaviour-preserving)

- Refactors come from a read-only audit against SOLID, Clean Code, GRASP and
  Object Calisthenics, applied one at a time, each covered by existing tests.
- Plans, numbers, reason codes, API schemas and `SCHEMA_VERSION` stay identical.
  Any refactor that would change an observable value is out of scope.
- Dependency direction stays inward: domain modules import no adapter, solver,
  web or persistence framework.

### Experiment narrative

- README rewritten in this order: the problem as lived in outpatient clinics
  (no employer or company names; the author's ten years in healthcare software
  are the only biographical fact), the hypothesis, the stages of the experiment
  in the order they were built (SF-001 to SF-010), the decisions taken at each
  gate and why, the evidence with its numbers, the no-go, the claim boundary.
- `docs/architecture.md` gains a layer description (domain, application,
  optimizer adapter, API boundary, persistence, UI, research scripts) and one
  decision traced end to end.
- Screenshots are produced by a Playwright script against the local API and
  Vite server, saved under `docs/images/`, and every capture shows the no-go
  strip (cycle 2 plan, SF-014 capture rule). No monetary value appears.

## Acceptance criteria

- [x] `make verify` passes before and after every refactor commit; the
      development comparison, the clinic-day demo and the API contract tests are
      unchanged.
- [x] No domain module (`domain`, `eligibility`, `strategies`, `optimizer`,
      `day_context`, `explanations`) imports FastAPI, Pydantic, sqlite3 or
      `api_*`.
- [x] README tells the experiment sequentially with the stage table linking each
      stage to its spec, its decision and its test file.
- [x] Every screenshot in `docs/images/` is generated by
      `web/tests/screenshots.spec.ts` and includes the no-go strip.
- [x] Publication-contract tests pass on the new README and docs (forbidden
      words, "proves" only with "within the declared model").
- [x] No company, clinic, provider or patient name appears anywhere.

## Rejection conditions

- a refactor changes any plan, metric, reason code or schema;
- a screenshot without the no-go strip, or any screenshot taken by hand;
- README text that converts the controlled result into a financial, access or
  clinical claim;
- a company or employer name in README or docs.
